# Plan for #3: Add DELETE /api/runs/:id

## Goal
Allow test engineers to delete a run through `DELETE /api/runs/:id`, returning 204 when deletion succeeds and removing the run from subsequent listings. Unknown IDs return the existing JSON 404 shape, while runs with status `running` remain protected with a 409 error.

## Dependencies (confirmed / plausible / open), each with change: yes | no
- confirmed: `src/runs.ts` — `RunStore` owns the in-memory `Map`; add a deletion operation that distinguishes missing, running, and deletable runs. change: yes
- confirmed: `src/app.ts` — route handlers and JSON error mapping live in `createApp`; register `DELETE /api/runs/:id`. change: yes
- confirmed: `test/app.test.ts` — supertest API coverage exists for runs; add success, unknown-ID, and running-status cases. change: yes
- confirmed: `README.md` — API table documents run routes and error shapes; document DELETE responses. change: yes
- plausible: `public/index.html` — it renders runs but has no delete control; no UI change is required by the ticket, verify scope remains API-only. change: no
- plausible: `e2e/smoke.spec.ts` — browser coverage only adds a run; no delete acceptance criterion. change: no
- confirmed: `src/config.ts`, `k8s/configmap.yaml` — deletion needs no environment setting or deployment change. change: no

## Tests
- `test/app.test.ts`: delete a planned seeded run, assert 204, then verify it is absent from `GET /api/runs`
- `test/app.test.ts`: delete an unknown ID, assert 404 and `{ error, id }`
- `test/app.test.ts`: mark a seeded run as `running` in the in-memory test store, then assert 409 and that the run remains present

## Environment contract
No variables are added or changed. `src/config.ts`, `k8s/configmap.yaml`, and the README environment table remain unchanged.

## Risks
- Deleting from the store must not accidentally alter ID sequencing or unrelated runs.
- The running-status guard depends on the current domain model and may expose a prerequisite gap if no status-update path exists yet.
- Incorrect route ordering or error mapping could turn `DELETE` into a 404/500 or violate the JSON error contract.
- Pipeline risks: unit test failures, while rollout, stability, smoke, and browser checks should remain unchanged unless the implementation affects startup or the page.

## Open questions
1. Should this remain API-only as written, or should the web page also expose a delete control and browser coverage?

## Decisions
- UI scope: API-only; do not add a delete control or browser coverage.
- Because no status-transition route exists yet, the running-status test sets the in-memory run state directly.
- Implemented in `src/runs.ts`, `src/app.ts`, `test/app.test.ts`, and `README.md`.
- `npm run verify` passed: lint, 11 unit tests, and build.
