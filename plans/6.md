# Plan for #6: Add run status transitions

## Goal
Add `PATCH /api/runs/:id/status` accepting `{ "status": ... }`, allowing only
`planned -> running` and `running -> done`. Invalid transitions return HTTP 409
with `error: "invalid transition"` plus `from` and `to`; unknown IDs return the
existing 404 JSON shape. No existing GET/POST behavior or UI behavior changes.

## Dependencies (confirmed / plausible / open)
- **Confirmed — change: yes:** `src/runs.ts` (`RunStatus`, `RunStore.get/create`)
  needs transition validation and mutation support for the in-memory run.
- **Confirmed — change: yes:** `src/app.ts` (`createApp`, route/error handling)
  needs the PATCH route, request-body validation, 404 mapping, and 409 mapping.
- **Confirmed — change: yes:** `test/app.test.ts` (`runs api`, supertest)
  needs happy-path, invalid-transition, and unknown-ID endpoint tests.
- **Confirmed — change: no:** `src/config.ts` reads only existing configuration;
  the endpoint requires no new environment variable.
- **Confirmed — change: no:** `k8s/configmap.yaml` provides the unchanged runtime
  configuration contract.
- **Confirmed — change: no:** `README.md` API/environment documentation is not
  part of this requested plan output; implementation should update its API table
  only if ticket scope later requires documentation changes.
- **Confirmed — change: no:** `public/index.html` only renders/creates runs, and
  `e2e/smoke.spec.ts` covers health/add-run; no UI workflow is requested.
- **Plausible — change: no:** `.github/workflows/ci.yml` should exercise the
  existing unit/build/deploy gates without workflow changes; verify in CI.
- **Open — change: no:** none; the ticket specifies the route, payload,
  transitions, status codes, and required tests unambiguously.

## Tests
- In `test/app.test.ts`, create a run and PATCH it from planned to running,
  then running to done; assert 200 and returned status.
- Assert a disallowed transition returns 409 with `error`, `from`, and `to`.
- Assert PATCHing an unknown ID returns 404 with the ID context.
- Run the existing unit, type-check, build, rollout/stability, smoke, and
  browser pipeline checks; no e2e test change is required.

## Environment contract
No variables are added or changed. `src/config.ts`, `k8s/configmap.yaml`, and
the README environment table remain synchronized without modification.

## Risks
- Transition logic must reject skipped/backward transitions without mutating
  the stored run.
- Malformed or unsupported status input must use the repository's JSON
  validation error convention rather than silently defaulting.
- A route ordering or error-mapping regression could affect existing GET/POST
  behavior; retain current tests and run `npm run verify`.
- Since deployment manifests are unchanged, rollout/stability, smoke, and
  browser failures would indicate a regression outside the intended surface.

## Open questions
None.

## Decisions
- Scope is API/domain logic plus `test/app.test.ts` coverage only.
- No environment, UI, Kubernetes/deployment, or CI workflow changes are needed.
- Implemented in `src/runs.ts`, `src/app.ts`, and `test/app.test.ts`.
- `npm run verify` passed with 11 tests.
